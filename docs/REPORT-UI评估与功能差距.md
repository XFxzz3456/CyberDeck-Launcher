## 第一部分：UI 整体评估

### 总评

这套 UI 的**视觉完成度明显高于同类工具的平均水平**：6 套主题有真实的形态差异（不是换皮）、封面随主题联动、硬件视觉语言（切角/噪点/警告带）贯彻一致、安全相关的交互模式（按住确认、冲突优先展示）成熟。字号经过上一轮审计已从 5.5–9px 提到 7–10.5px，今天又修掉了设置页的低对比重灾区。**剩下的问题不再是「哪里坏了」，而是「信息密度、状态可发现性、空状态引导」三类的打磨。**

### A. 可读性与排版（优先级：高）

**A1. 正文实际渲染尺寸仍然偏小**
- 现象：截图里卡片描述、类别列表、面板说明实测约 10px 上下；主流程文字（mod 描述、诊断说明）也仅 10–10.5px。中文在 10px 以下笔画粘连，1080p 全屏时更明显。
- 建议：下一个迭代把「阅读型文字」（描述/说明/提示）下限提到 11–12px，仅保留「装饰性文字」（kicker、版本号、坐标类 mono 标签）在 9–10px。可以只调 `--muted` 系的规则组，不动数据标签。
- 代价：信息密度下降，卡片高度、列表行高需要联动；虚拟滚动的 `rowHeight=328` 需要重新校准。**这正好是上轮审计没做完的「字号第二档」工作。**

**A2. 行高与字距偏紧**
- 现象：多处 `line-height: 1.45` 以下 + `letter-spacing: 1px` 的中文长句（如设置页说明）扫读困难。
- 建议：中文长句行高 ≥1.6；`letter-spacing` 只留给纯西文/数字的 mono 标签，中文文本取消字距。

**A3. 诊断页 warning 色对比仍差一步**
- UI-AUDIT 自己已记录：`#a8620a` 在纸白底上约 4.4:1，未达 WCAG AA 4.5:1。
- 建议：Daylight 主题的 `--orange` 压深一档（如 `#8a4e06`），一处 token 改动即全局生效。

**A4. 中文字体回退未指定**
- README 说「中文回退到微软雅黑」，但雅黑在小字号下渲染发虚。建议 font stack 在 Inter 后插入 `Microsoft YaHei UI` 并对中文正文考虑 `text-rendering` 优化；更进一步的选项是本地打包思源黑体子集（代价：体积 +2–4MB）。

### B. 信息架构与状态可发现性（优先级：高）

**B1. 顶栏是全局状态的唯一入口，但侧栏不呼应**
- 现象：冲突数、体检结果、熔断横幅都只在特定页面出现。用户在模组库时不会知道诊断页有 1 个 critical。
- 现有基础：侧栏「运行诊断」已有红色徽标 `1`，这是个好模式。
- 建议：把徽标推广到全部状态入口——加载顺序项（冲突数）、设置项（有未保存变更时）、Nexus 项（Key 失效/未登录）。规则：**任何需要用户行动的状态，必须在侧栏有一个可达的数字**。

**B2. 搜索只有「当前页」语义**
- 现象：搜索框过滤当前视图，但用户不知道范围。命令面板（Ctrl+K）承担了全局跳转却藏在快捷键后。
- 建议：搜索框 placeholder 已写「搜索模组」——加一个「范围：全部/本分类」的轻量提示；命令面板按钮在顶栏露出（点击也行，不只 Ctrl+K）。

**B3. 空状态是全项目最薄弱的引导位**
- 现象：`STAGING EMPTY` 面板视觉不错，但只有一个「导入」按钮。新用户第一次打开时最需要的 3 件事——绑定游戏目录、了解部署模型、去 N 网找模组——都没有入口。
- 建议：空状态按「缺什么补什么」动态给 1 主 1 次两个动作：未绑游戏目录时主按钮变「绑定游戏目录」；已绑定时给「去发现页看看」次级链接。不改结构，只改 EmptyState 的 props 逻辑。

**B4. 播放集切换的后果不可预览**
- 现象：播放集切换是「快照→撤全部→再部署」的重操作，但 UI 只有一个「切换」按钮，用户不知道要等多久、游戏目录会发生什么。
- 建议：切换前弹确认卡：列出「将撤除 N 个文件 → 将部署 M 个文件」，并把进度事件（后端已有四段式流程）映射成步骤指示器（撤除中→写入中→部署中）。这是**信任感**投资，也是架构文档 ADR-003 的 UI 侧配套。

### C. 交互与反馈（优先级：中）

**C1. 危险操作的确认模式很好，但缺少「最近做了什么」**
- 现象：任务中心管导入队列，但部署/撤除/切换播放集完成后只有短暂 toast。用户回神后不知道刚才那一下改了多少文件。
- 建议：给顶栏或侧栏加一个轻量「活动流」（最近 10 条：时间 + 动作 + 文件数），复用任务中心的数据结构即可。

**C2. 拖拽导入的落点反馈**
- 现象：窗口任意处拖入压缩包可导入（功能在），但缺少拖拽悬停时的全屏落点高亮（虚线接收框只在空状态/设置页可见）。
- 建议：dragover 时全屏显示接收层 + 文件计数。纯前端事件，成本低、感知收益大。

**C3. 长列表的滚动位置在筛选后丢失**
- 现象：切分类/搜索后虚拟网格回顶。用户在 500+ 模组里来回对比时很痛苦。
- 建议：同分类筛选变化时保留滚动锚点，或提供「返回之前的位置」小浮标。

### D. 视觉一致性（优先级：中低）

**D1. 卡片内层级仍靠「红」**
- 现象：ARASAKA 下卡片描边、STAGED 徽标、角标、文件统计全是同一族红。上轮已降饱和，但「状态徽标」与「装饰描边」仍未分家。
- 建议：给状态徽标建立独立语义（STAGED=中性灰描边、DEPLOYED=绿、CONFLICT=红），描边降为纯结构线。这是把「冲突 > 已部署 > 暂存」的状态优先级从文字提升到颜色编码，符合现有 token 体系（`--ok`/`--danger` 已存在）。

**D2. 图标语言混用**
- 现象：lucide 图标 + 自绘几何标记（`VX`/`NC`/`2077` 封面字）+ emoji 无，整体尚可，但设置页各 section 的图标与侧栏不完全成对。
- 建议：建立一份「图标-概念」对照表（模组库/部署/冲突/备份各一个图标），写进 UI-AUDIT 文档作为约束。

**D3. 主题缩略图会过期**
- UI-AUDIT 已知项：主题配色改动后缩略图滞后，且裁图脚本没有固化。
- 建议：把裁图固化成 `scripts/make-theme-thumbs.mjs`，并在 `audit-shots.mjs` 末尾自动调用。

### E. 性能与工程健康（优先级：中）

**E1. bundle 超过 500kB 警告**
- 构建日志提示 chunk 过大。建议按视图做动态 import（Nexus 发现页、诊断页是天然分割点）。对启动速度有实感收益。

**E2. `styles.css` 已 9700 行单文件**
- 所有主题、组件、状态样式在一个文件里。建议按「token 层 / 形态层 / 组件层」拆成 3 个文件（Vite 自动合并，无运行时代价），否则下一个人改样式的心智负担会持续上升。

**E3. mock.ts 与真实 schema 的漂移风险**
- mock 是浏览器演示/UI 测试的数据层，字段靠手工同步。建议给 mock 数据加一个从 `types.ts` 派生的类型断言（编译期校验），防止新字段只加在 Rust/TS 侧、mock 漏改。

## 第二部分：对标 Nexus Mods App 的功能差距

对照对象：Nexus Mods App 官方公开功能（Collections、Loadout 管理、Health Check、Workspace 多面板、自动更新检查、External Changes 检测、多游戏、跨平台）+ 你截图中的官方界面（合集/浏览 N 网/加载程序/工具/健康检查/配置文件/游戏设置 + 列表列：版本/分类/依赖/更新检查）。

**先说结论：NCL 在「部署模型的正确性」上其实领先**——安装/部署分离、硬链接+身份校验、只信 deployed_files 清单、冲突预检拦截，这些 Nexus App 目前仍在用「复制+自有目录+External Changes」的方式处理。差距集中在「生态连接」和「自动化」两层。下表按「符合项目定位与否」分列：

### 值得补的差距（符合「导入→部署→排序→诊断」定位）

| # | 功能 | Nexus App | NCL 现状 | 建议 |
|---|---|---|---|---|
| 1 | **模组更新检查** | 自动扫描已装模组的新版本、批量更新 | 无。Nexus 导入后与源头断联 | 用已有 `ModEntry.nexus {modId, fileId}` 调官方 API 批量比对 file id/上传日期；列表页加「有更新」徽标 + 一键跳转下载页。**不做自动覆盖安装**（符合「危险操作须确认」原则），只做「发现 + 引导」 |
| 2 | **整合包集合报告** | Collections 一键安装 + 缺失检测 | 整合包导入已有；HANDOFF P5 明确缺「缺失模组 / 版本不匹配报告」 | 按原计划做：解析包内清单 → 对照本库 → 出「缺失/版本不符/将冲突」三类报告。**不做 N 网集合的一键全量下载安装**（Premium 依赖 + 批量静默安装违背逐项确认原则） |
| 3 | **缺失前置的引导闭环** | 健康检查给出「一键安装依赖」 | 诊断能报「缺 RED4ext/CET」，但没有安装引导 | 诊断结果卡片加「跳转到官方发布页」按钮（走现有 `open_url` 白名单）。不代下载、不代安装，零安全成本 |
| 4 | **依赖列（依赖关系可视化）** | 列表有 Dependencies 列、图状依赖 | 只有保守推断的前置提示 | 短期在详情抽屉里把「推断出的前置」从文字提示升级为结构化列表（框架 + 满足/缺失状态）；**不冒充作者声明的完整依赖图**（README 已明确该边界） |
| 5 | **External Changes 的用户沟通** | 卸载管理时警告会删除既有 mod | 有 unmanaged 文件检测 + 永不覆盖，但入口埋得深 | 冲突中心已有「未受管文件」类目，把它提升到诊断页摘要的第一屏，配一句「这些不是启动器部署的，永不会被自动删除」 |
| 6 | **游戏设置面板** | 有游戏参数设置区 | 有启动方式/平台选择，但启动参数（如 `-modded`、自定参数）不可编辑 | 加一个「启动参数」输入框（白名单校验），配合现有 launch_game 即可 |
| 7 | **通知中心** | 有通知/更新提醒 | 任务中心只管进行中任务 | 把 C1 的「活动流」与「更新检查结果」合并成一个铃铛入口（你截图的官方 UI 同款位置） |

### 明确不追的差距（与项目「明确不做」一致）

| 功能 | 为什么不做 |
|---|---|
| N 网集合（Collections）一键批量安装 | 需要 Premium + 批量静默安装，违背「逐项确认」与 Nexus 边界；集合报告（上表 #2）是正确替代 |
| Workspace 多面板并排 | 单窗口单任务流是定位；多面板是 N App 押注的差异化，不适合小团队跟进 |
| 多游戏支持 | README 明确只服务 CP2077；domain 层已按游戏无关组织，未来想做时再评估 |
| Linux / Steam Deck | Windows-only（Win32 API 深度耦合：DPAPI、硬链接身份校验、VerQueryValue） |
| 游戏内 overlay / 进程注入 | 明确不做（README） |
| 账号收藏同步、社区互动（点赞/评论） | 超出工具定位；且 N App 自己也在收缩这块 |

### NCL 反超的点（对比时应该保持并宣传）

1. **部署即链接，不留管理器税**：N App 卸载管理会清空游戏目录既有 mod；NCL 永不碰 unmanaged 文件。
2. **硬链接同卷零拷贝**：N App 主要走复制/硬链接到自有受管目录；NCL 直接在游戏目录建链接，磁盘与时间都省。
3. **全量离线可用**：核心功能（导入/部署/排序/体检）不登录、不联网。
4. **AI 诊断的隐私边界**：脱敏 + 逐次同意 + 白名单 focus，比 N App 无此能力。
5. **环境体检自愈**：从暂存区重建丢失链接，N App 的 Health Check 只报告不修复链接层。

## 第三部分：建议的执行顺序（并入现有路线图）

1. **0.7.x 剩余**（本周）：真机验收 + 上面 A1/A3/B3/D3 这类低成本高感知项。
2. **0.8 结构期**（已开工：Profiles 已完成大半）：补 B4 播放集切换进度指示器（后端事件已就绪）+ 模组更新检查（#1，纯只读 API）。
3. **0.9 分发期**：维持原计划（签名/Updater）。
4. **1.0**：集合报告（#2）+ 依赖引导闭环（#3/#4）。

> 一句话：**UI 的下一步不是再换皮，而是「把字号/对比度收尾 + 把状态可发现性做穿」；功能上用「只读的生态连接」（更新检查、报告、引导）对齐 N App，绝不跟进它的批量自动化。**
