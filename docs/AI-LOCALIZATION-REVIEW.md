# AI 深度汉化 — 架构评审（0.9.0 · 对应看板【8】）

> 状态：评审结论已定，实施分三期。本文件是【8】的第一交付物；编码按里程碑推进，不在本轮一次性铺开。
> 关联：看板【7】名称级词表共享（已实现名称/描述的云端词表底座）、`docs/REPORT-架构设计与长期规划.md`。

## 一、红线（不可协商）

1. **不做游戏内 overlay、不做进程注入、不做实时翻译**。任何"运行中替换 UI 文本"的方案一律否决——它与反作弊、稳定性、法律风险三重冲突，且无法回滚。
2. **不修改原 Mod 文件**。所有产物写到独立目录，登记进 `deployed_files`，卸载时按清单撕除。
3. **不覆盖用户本地自定义译文**。词表合并永远是「本地优先」。
4. 框架名（RED4ext / ArchiveXL / TweakXL / CET / REDscript / ModSettings / WolvenKit 等）**进黑名单免翻译**，规则与现有 `ai.rs` 保持一致。

## 二、三条候选路线与裁决

| 路线 | 做法 | 可回滚 | 风险 | 结论 |
|---|---|---|---|---|
| A 离线生成本地化资源 | 生成独立覆盖层（.archive + .xl / 本地化 JSON / 框架菜单配置），随部署进游戏 | 是（清单撕除） | 低 | **采用** |
| B 运行时 overlay | 注入进程改 UI 文本 | 否 | 高（反作弊、崩溃） | **禁止** |
| C 仅词表替换 | 只翻名称/描述，显示在启动器内 | 是 | 无 | 已实现，作为 A 的词表底座 |

## 三、范围与写入白名单（M1 只做前三类）

| 目标 | 载体 | 写入位置 | M1 是否做 |
|---|---|---|---|
| Mod 名称 / 描述 | 启动器内显示（词表） | 不进游戏目录 | 已上线 |
| 本地化 JSON（mod 自带 `localization/*.json`） | 新增覆盖 `.archive` + `.xl` | `archive/pc/mod/<modId>-ai-loc.archive/.xl` | 是（需 WolvenKit CLI） |
| CET 菜单项与选项说明 | `user.ini` 的注释/标签文本 | **不直接改原文件**；生成 `ai-loc/<modId>/user.ini.patch` 供人工确认后合并 | 是（只生成补丁，不自动写） |
| RED4ext 插件菜单（TOML/JSON） | 插件配置副本 | `ai-loc/<modId>/<plugin>.toml` | 否（M2） |
| 通知文本 | 游戏内 `.json` 本地化 | 同本地化 JSON | 否（M2） |

写入白名单硬约束：
- 所有路径先过 `store::safe_join` + `is_within`，越界直接拒绝（复用现有实现，不新写一套）。
- 目标文件名必须带 `-ai-loc` 后缀，便于人工识别与一键清理。
- 原 Mod 文件只读打开，产物写到 `staging/ai-loc/<modId>/`。

## 四、词表：主键、冲突与失效

- 主键 = `mod_id + hash(原文)`（【7】已实现）。**mod 更新后原文变化 ⇒ 主键不命中 ⇒ 自动重译**，不需要版本迁移逻辑。
- 合并优先级：本地自定义 > 云端共享 > AI 新译。
- 冲突（同一主键两条云端译文）：保留 `updated_at` 较新者，另一条进 `conflicts` 计数，界面可查。
- 纠错入口：词表卡片支持按 mod 列出条目并就地编辑（M2），编辑后标记为 `by: "local"`，永不被云端覆盖。
- 框架名黑名单在**词表命中之前**生效：黑名单词即使云端有译文也不采用。

## 五、生成与部署流程（M1）

```
选目标 Mod → 读原文（只读）→ 词表命中? ─ 是 → 用词表
                                   └ 否 → 调 AI（逐条，带 JSON 约束 + ```json 剥壳）
        → 生成覆盖层到 staging/ai-loc/<modId>/
        → 校验（archive 可被 WolvenKit 读取、.xl 指向自身）
        → 部署（走既有 deploy_mod，登记 deployed_files）
        → 失败整批回滚（复用现有回滚实现）
```

关键约束：
- **AI 返回必须是纯 JSON**：Anthropic 不支持 `response_format`，统一用 prompt 约束 + 现有剥壳逻辑；解析失败整条丢弃并计入 `failed`，不写半成品。
- 单 Mod 生成上限（默认 200 条），超限分批，任一批失败不影响已成功批次（与翻译任务同语义）。
- 生成期间不持 `store.data` 锁（`Mutex` 不可重入，见 `profiles.rs` 头注释的同类教训）。

## 六、回滚与"Mod 更新后重做"

| 场景 | 处理 |
|---|---|
| 用户关闭汉化 | 按 `deployed_files` 撕除 `-ai-loc` 文件，原 Mod 不受影响 |
| Mod 升级 | 覆盖层按新原文重建；旧覆盖层先撕除再部署（避免残留旧译文） |
| 游戏大版本更新 | 覆盖层可能失效：环境体检增加"覆盖层与当前游戏版本不符"提示，一键重建 |
| 产物损坏 | 删除 `staging/ai-loc/<modId>/` 后重建；词表不受影响，无需重新调 AI |

## 七、验收（M1）

- [ ] 同一 Mod 二次生成**不产生重复调用的 AI 费用**（词表命中率 ≥ 95%，日志可证）
- [ ] 关闭汉化后，游戏目录中 `-ai-loc` 文件数为 0，原 Mod 文件 mtime 未变
- [ ] Mod 升级后旧覆盖层被撕除，新覆盖层生效
- [ ] 框架名黑名单词零翻译（单测断言）
- [ ] 越界路径注入（`../`）被拒并有明确报错
- [ ] 生成失败不写脏状态：状态文件 md5 不变（单测）

## 八、不做清单（明确划界，防止范围蔓延）

- 不做游戏内实时字幕 / 悬浮窗翻译
- 不做对他人作品的二次分发打包（只在本机生成）
- 不做语音/配音本地化
- 不做云端译文审核后台（M3 之后另立项）
