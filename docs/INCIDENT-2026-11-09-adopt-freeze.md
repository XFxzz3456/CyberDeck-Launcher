# 事故复盘：收编扫描冻结与 159 条批量失败（2026-11-09）

> 用户固定要求「每次修完 bug 都要总结得失」。本文按「现象 → 真因 → 走过的错误假设 → 代价/新约束 → 下次第一步查什么」记录。
> 现场排查报告（含模拟扫描数据）见工作区 `CyberDeck-收编卡顿与批量失败排查-2026-11-09.md`。

## 1. 现象

用户在 release 1.3.1 上连发两张截图：

1. 21:21 「收编既有模组」弹窗停在 `正在扫描 archive/pc/mod…`，窗口标题已是 `CyberDeck (未响应)`，整窗灰化（Windows ghosting），`开始收编 (0)` 置灰。
2. 21:22 收编结果 `模组 284 / 文件 4076 / 4.0 GB / 可勾选 204` → `成功 45 · 失败 159 · 跳过 0`，失败条目成片 `ADOPT_STAGING_FAILED`，按钮 `重试 (159)`。

现场体检：库里 106 条模组、staging 149 个目录，其中 **44 个孤儿目录**，另有 **1 条已登记模组 `adopt-2768f94e6857836a` 的暂存目录已丢失**。

## 2. 真因（三条，均已用代码与现场数据确证）

1. **扫描跑在主线程。** `lib.rs:476` 的 `adopt_scan` 是非 `async` 的 Tauri 命令，注释写着「扫描是纯只读操作，同步即可」。但 `adopt::scan` 实际遍历 225 个 Vortex 目录树（深度 8）、对 4076 个文件逐个 `fs::metadata`、打开 LevelDB、对每个候选算 `same_volume`。`adopt_execute` 早已用 `spawn_blocking`，扫描漏了。库一大就冻窗口，用户只能强杀。
2. **失败原因被藏进 tooltip。** `AdoptPreviewDialog.tsx:256` 只渲染 `error.code`，`error.message`（四种具体原因）只放在 `title`。159 条失败排成一模一样的一列，等于静默失败——违反项目红线「任何失败必须在界面上可见」。
3. **失败回滚会删库内暂存目录。** `materialize` 撞上 `target.exists()` 就报 `ADOPT_STAGING_FAILED`，`rollback_staging` 随后无条件 `remove_dir_all(staging_base/<candidate.id>)`。若该 id 属于一个已登记模组，这次「回滚」删的是库内资产。现场那条缺失的暂存目录就是这么来的；强杀窗口留下的半成品目录则变成 44 个孤儿，并在重跑时继续触发 `暂存区已存在同名文件`，形成失败闭环。

## 3. 走过的错误假设（全部排除，按排查顺序）

| 假设 | 排除依据 |
| --- | --- |
| Vortex 在收编期间并发部署、把游戏侧文件搬走 | Vortex 进程未运行，`vortex.log` 最后写入 11-09 00:12（关机），与 21:22 相隔 21 小时 |
| 跨卷复制撑爆磁盘 | 游戏目录与 Vortex 存储根同在 D 盘，剩余 110 GiB，4 GB 批次不构成压力 |
| Windows 路径超长（MAX_PATH） | 逐个复刻 `safe_join` / staging 拼接，超长 0 条 |
| 文件名大小写冲突导致暂存撞车 | `archive/pc/mod` 与 Vortex 目录内大小写冲突均 0 |
| `normalize_rel` 的 trim 让路径指向不存在的文件 | 复刻后逐个 `is_file()`，缺失 0 条 |
| `scan_dirs` 把不存在的文件放进候选 | 该函数本来就按 `game_root/rel.is_file()` 过滤 |

排除这些之后，「上一轮强杀留下残留暂存目录 → 重跑撞车 → 回滚又删」是唯一能同时解释「大文件数候选全挂、单文件候选成功」与「44 孤儿 + 1 缺失」的路径。**159 条的最终 message 未取到**（界面当时不显示），需用户悬停红色错误码给出 tooltip 原文才能 100% 定案；修复后新失败会直接显示原因。

## 4. 代价与新约束

**代价**：一次收编操作让库进入不一致状态——44 个孤儿暂存目录、1 条已登记模组无暂存目录（禁用/卸载可能受影响）；用户被迫强杀窗口，且看不到任何可据以自助排错的信息。

**新约束（已写进代码与文档）**：

- 任何会做磁盘遍历的 Tauri 命令一律 `async` + `spawn_blocking`，「只读」不等于「不阻塞」。
- 失败详情必须在渲染层内联展示，错误码降级为 `title`；不允许只给 code。
- 回滚/清理必须带归属校验：批次开始时已在库里的 id 全程受保护，失败时宁可留多余硬链接也不删库内目录。
- 已登记且暂存目录还在的候选在扫描阶段直接标 `already_managed`，不进执行批次。
- 体检类命令**只列不删**；孤儿目录清理必须用户单独确认，且不在取证命令里顺手做。

## 5. 下次第一步查什么

1. 卡「未响应」→ 先查命令签名是不是 `fn` 而不是 `async fn`，以及有没有 `spawn_blocking`；不要先怀疑磁盘或杀软。
2. 成片同一个错误码 → 先查渲染层是否把 `message` 藏了；把原因显示出来再谈根因。
3. 任何「失败后清理」→ 先查清理目标的归属集合是否来自「批次开始前」的库状态，而不是当前候选 id。
4. 批量失败且伴随孤儿目录 → 先怀疑上一次被强杀的批处理留下半成品，而不是本次 IO。

## 6. 本轮修复

- `adopt_scan` 改 `async` + `spawn_blocking`。
- `AdoptPreviewDialog` 内联展示 `error.message`，CSS 允许换行。
- `rollback_staging` 接受 `protected` 集合；`execute_inner` 额外拦截已登记候选；`scan` 把已登记且暂存目录存在的候选标 `already_managed`。
- 新增 `adopt_staging_health`（只读）与设置页「Vortex 接管体检」卡片，列出孤儿/缺失目录与 Vortex 状态漂移，**不删任何文件**。
