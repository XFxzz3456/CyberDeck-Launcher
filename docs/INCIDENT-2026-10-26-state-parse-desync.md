# 事故复盘（2026-10-26 深夜）：反序列化器未消费输入 → 状态文件被判损坏 → 195 条模组索引被清空

> 严重级别：高（数据丢失，但可恢复）
> 影响范围：Brand 改名 + Nexus Collections 清理那一轮
> 恢复结果：已从 `.broken` 备份完整恢复（195 mods / 125 条 loadOrder / nexus 引用全在），并加了回归测试

---

## 1. 现象

- 06:13 改名后的首次启动，日志显示 `load ok`，但界面里**模组全没了**；
- 数据目录里出现 `launcher-state.broken-20261025-221357.json`（365KB，完整内容），
  紧接着是一份 968 字节的**空状态** `launcher-state.json`；
- 之后每次启动都把空状态再写一遍，并继续产生新的 `.broken`；
- **游戏目录里已部署的模组文件本身没丢**，丢的是启动器的索引（JSON）。

## 1.5 严重性更正（后经系统性复测）

初版复盘把它描述为"升级那一刻丢一次索引"，**低估了**。系统复测三种形态后确认：

| 状态文件里的 `modpacks` | 结果 |
|---|---|
| `"modpacks": []` | **解析失败** |
| `"modpacks": ["x"]` | **解析失败** |
| 没有该字段 | 解析成功 |

**空数组同样会炸**，而空数组正是启动器**每次落盘都会写出的形态** → 那个版本是
**每次启动都把用户的模组库清空一次**，而不是只在升级那一刻。
（那次"丢了 195 条"其实是被反复清空的结果；游戏目录里的文件始终没丢。）

## 2. 真因

Nexus Collections 清理时，为了"一次性作废旧整合包记录"，在 `schema.rs` 里加了一个自定义反序列化器：

```rust
#[serde(default, deserialize_with = "deserialize_always_empty")]
pub modpacks: Vec<ModpackEntry>,

fn deserialize_always_empty<'de, D>(_: D) -> Result<Vec<ModpackEntry>, D::Error> {
    Ok(Vec::new())          // ← 反序列化器参数被丢弃，输入值从未被消费
}
```

serde 的自定义 `deserialize_with` **必须把输入值消费掉**。这里直接把 `D` 丢进 `_`，
于是 serde 解析完 `"modpacks":` 之后，**解析器还停在数组的开头**，而外层 map 解析器
以为当前还缺一个值 → 报 `expected ',' or '}' at line 9392 column 15`（正是 `"modpacks": []` 的 `]` 位置）。

后果链：**整个状态文件解析失败** → `store.rs` 判定"文件损坏" → 把它重命名为 `.broken` 并
**用空状态继续启动** → 随后的落盘把空状态写回磁盘 → 195 条模组索引、加载顺序、设置全部消失。

讽刺的是：改动的**意图**是"让旧 modpacks 记录不再碍事"，实际效果是"让整个文件废掉"。
**触发时机恰好撞上品牌改名**（同一轮里既有数据目录搬迁、又有 schema 变更），所以第一反应是"改名把数据写坏了"，其实数据本身一直是好的，是解析器不认它。

## 3. 走过的弯路

1. 先怀疑**我的 Python 改写把 JSON 写坏了**（用 `json.load` 能读通 → 以为 JSON 语法没问题）；
2. 再怀疑**品牌改名改了枚举/字段名**导致 schema 不匹配（逐字段对比键名与类型，全部一致）；
3. 最后用**探针测试**直接让 Rust 解析那个 `.broken` 文件，才拿到确切错误：
   `expected ',' or '}' at line 9392 column 15` —— 一个**语法**错误，而不是 schema 错误，
   这才把方向从"数据被改坏"掰回到"反序列化器没消费输入"。

## 4. 修复

```rust
fn deserialize_always_empty<'de, D>(deserializer: D) -> Result<Vec<ModpackEntry>, D::Error>
where D: serde::Deserializer<'de>,
{
    // 必须先消费掉输入值（用 IgnoredAny 跳过，不要求旧结构能对上类型），
    // 否则 serde 的解析位置会错位，整个状态文件会被判为「损坏」并被重置为空。
    let _ = <serde::de::IgnoredAny as serde::Deserialize>::deserialize(deserializer)?;
    Ok(Vec::new())
}
```

同时新增回归测试 `schema::modpacks_cleared_on_load::modpacks_field_is_ignored_but_still_consumed`：
喂一份带旧 `modpacks` 数组的状态，断言**能解析**且 `modpacks` 为空——把这次的坑钉死在测试里。

## 5. 沉淀成规则

### 5.1 serde 自定义反序列化器
- `deserialize_with` 的函数**必须消费输入**；要"忽略并置空"就用
  `IgnoredAny::deserialize(deserializer)?` 再返回空值；
- 写这类函数时**必须配一个解析测试**：喂真实结构的旧数据，断言能解析成功。
  只断言"字段是空的"是不够的——空数组和不消费输入，前者能过测试，后者同样能过，
  差别只在**整个文件**能不能解析。

### 5.2 状态文件的容错策略
- `store.rs` 遇到解析失败会**静默重置为空状态**（保留 `.broken` 备份，这点是对的）；
  但"静默重置"会掩盖"我的新代码让旧文件解析不了"这类回归。
  → 建议：解析失败时把**错误原因**写进 `startup.log`，并在界面上提示"状态文件解析失败，
  已保留备份"，别让用户以为模组凭空消失。

### 5.3 一次性数据迁移
- 改 schema / 改字段语义时，**必须用真实旧数据跑一次解析**（本项目的真实数据在
  `nightcity-data`/`cyberdeck-data` 里），不能只靠单元测试的构造样本；
- 本轮教训：单元测试全绿 ≠ 旧数据能读。

### 5.4 品牌改名
- 改名脚本要**避开数据格式值**：持久化的枚举取值（`origin: "nightcity"`）、临时文件前缀、
  localStorage 键名都属兼容锚点，改动必须有配套迁移；
- 更重要的是：改名那一轮**同时叠加了 schema 变更与数据搬迁**，一旦出问题极难归因。
  → 以后"改名 / schema 变更 / 数据迁移"三类改动**分三次提交**，一次只动一个变量。

## 6. 交付前必答三问

1. **哪个观测值证明了结论？** 探针测试打印出的 `expected ',' or '}' at line 9392 column 15`
   （语法错误 ⇒ 不是 schema/数据被改坏，而是解析器位置错位）；
2. **修复代价与新约束？** 反序列化器必须消费输入（不能再"无视参数"）；
   回归测试成为强制项；此后改 schema 必须用真实旧数据验证；
3. **下次第一步查什么？** 状态文件读不出来时，**先让 Rust 直接解析那个文件拿到错误信息**，
   不要先怀疑数据被改坏、更不要先动数据。

## 7. 数据恢复记录

- 恢复源：`launcher-state.broken-20261025-221357.json`（改名后、解析器修复前的完整状态）；
- 恢复结果：`mods=195`、`loadOrder=125`、`modpacks=0`（按产品决定清空）、nexus 引用完整；
- 保留件：`cyberdeck-data/launcher-state.pre-fix-backup.json`（365KB，确认无误后可删）；
- 游戏目录中已部署的模组文件**全程未受影响**。

> 🔴 **规则**：`deserialize_with` 的自定义反序列化器**必须消费掉输入值**
> （`IgnoredAny::deserialize(deserializer)?`）。否则 serde 解析位置错位 → 整个状态文件被判损坏 →
> `store.rs` 静默重置为空。**空数组形态同样会触发**，而空数组恰是启动器每次落盘都会写出的形态。
>
> 写这类实现时**不能只断言"结果为空"**——"空结果"与"整个文件坏掉后重置成空"在断言上无法区分；
> 必须断言"**整个状态文件仍能正常解析**、其它字段原样保留、**不产生 `broken-*.json`**"。

## 8. 追加（同日 23:41）：真正的损坏路径暴露了第二层问题——恢复过程静默

上面修的是"我们自己把文件写坏"。同一天夜里做 NXM 真机验收时，**外部工具把状态文件写坏**，
于是走到了同一条恢复支路，暴露出另一个缺陷。

### 现象

- 为临时关闭自动下载，用脚本对 `launcher-state.json` 做了一次
  「读 → 解析 → 重新序列化 → 覆盖」的整文件往返；
- 生成的文件 566KB 但结构非法；
- 重启后 `stage=frontend mods=0`，界面空空如也，**没有任何提示**；
- 数据目录里出现了 `launcher-state.broken-20261026-154119.json`（566KB，原文完整）。

### 结论：数据没丢，是"没说话"

`store.rs` 的恢复支路本来就是对的（改名保留 `.broken-*.json`、再建空状态）。
问题是**它只往 stderr 写一行**，而打包后的 exe 是 `windows_subsystem="windows"`，
没有控制台 → 那行等于写进虚空。用户看到的是"我的 195 个模组被启动器删了"。

### 修复

- `Store` 新增 `recovered_from`，`load()` 里命中恢复支路时记下 `.broken` 路径；
- `Snapshot.state_recovered_from` 把它带到前端；
- 界面顶部出现红色 `STATE RECOVERY` 条：说明**原文件已改名保留在哪个路径**、
  **这份空库一旦保存会写成新文件、恢复前别动**；
- 回归测试两项（`store.rs::recovery_tests`）：坏文件必须保留原文且被上报；正常文件不得误报。

### 付出的代价 / 教训

- 代价：我为了"安全地改一个布尔值"去做整文件往返，反而制造了损坏。
- 正确做法是用 Python（`json.load`/`json.dump`）改单个字段，或者直接用界面改；
  更根本的一条：**用户数据文件不要用「解析后重新序列化」的方式回写**。
- 教训：「数据被保留」和「用户知道数据被保留」是两件事。
  任何"降级到空/默认"的路径，都必须有一条**面向用户**的出口，
  否则等于静默重置。

> 🔴 **规则**：凡是"读不出来 → 退回默认值"的分支，必须同时产出
> （a）保留原件、且在文件名/路径上可辨认；
> （b）一条用户可见的提示，写明原件在哪、当前处于什么降级状态、恢复前别做什么；
> （c）一条断言该提示存在的回归测试。
> 只写 `eprintln!` 不算"告知"——打包后的 GUI 进程没有 stdout。
