> 结论：**P0 与 P1 全部关闭，P2 部分修、部分登记为不改**。门禁 27/27 全绿。

## 0. 为什么要「量化」

这份任务书原本要求「地毯式自查 + P0/P1/P2 分级报告」。人工看截图只能抓到明显错位，抓不到三类问题：

- 2560 屏下内容铺满 2300px——截图缩到 1080 宽看起来「很正常」
- 10px 灰字对比度 3.46:1——肉眼只觉得「有点淡」，不知道差 WCAG 多少
- 可点控件没有 `:active`——静态截图完全看不出来，只有真按下去才发现没反馈

所以先做了一个量化脚本 `scripts/check-ui-audit.mjs`，把能测的全变成数字，报告里直接引用实测值，而不是「看起来还行」。

覆盖九项：四档分辨率内容宽度、长文本溢出、80%/125%/150% 缩放、两套主题对比度、字号离群、表单左右对齐、hover/active 规则、页面报错。

## 1. P0 — 已修

### P0-1 超宽屏无最大宽度，正文铺满 2300px

| 项 | 数据 |
|---|---|
| 实测（修复前） | 2560×1440 下内容宽度 **2300px**，右侧留白 **0** |
| 影响 | 一行能塞 8 张卡片，正文行长超过 100 字，眼睛横向扫描成本高；1920 以上屏幕全部吃亏 |
| 修复 | `.page` 加 `max-width: 1680px` + `margin-inline: auto` |
| 实测（修复后） | 内容宽度 **1680px**，右留白 **310px** |
| 为什么是 1680 | 1920 屏下 `.content` 只有约 1660px，1680 不触发 ⇒ **1920 及以下零回归**；2560 屏才收进来居中 |

### P0-2 次要文字对比度低于 WCAG AA

| 项 | 数据 |
|---|---|
| 实测（修复前） | 深色主题下 5 处不达标，最低 **3.46:1**（要求 4.5:1） |
| 具体元素 | `--muted-2` = `#767a83`，被 `.mod-meta`（8px 卡片元数据）、`.conflict-block-head`（10px 冲突表头）使用 |
| 为什么难发现 | 8-10px 的小字尤其吃对比度，但视觉上只是「有点淡」，不测就不知道差了 1 个点 |
| 修复 1 | `--muted-2`：`#767a83` → `#82868f`，深色实测 **4.2 → 5.0:1** |
| 修复 2 | `.mod-meta` 的硬编码 `#687483`（实测 3.8:1）改为 `var(--muted-2)`，跟随主题 |
| 实测（修复后） | 两套主题 **0 处不达标**（`contrastFails=0`，浅色也是 0） |

## 2. P1 — 已修

### P1-1 四个主要交互控件没有按下反馈

| 类 | hover | active（修复前） |
|---|---|---|
| `.nav-item`（侧栏导航） | 有 | **无** |
| `.mod-card`（模组卡片） | 有（浮起 -2px） | **无** |
| `.settings-tab`（设置标签） | 有 | **无** |

原 9-9.5px 的中文说明（设置项描述、表单标签、可点按钮文字）笔画会糊。修三处：

| `.switch-desc` | 9.5px | 11px | 设置项中文说明：「会覆盖 ASCII 加载顺序…」 |

## 3. P2 — 登记但不修

### P2-1 装饰性小字保留 8-9.5px（27 处）

`titlebar-game` 9.5px、`logo-sys` 7.5px、`appearance-badge` 8px、`kbd` 8.5px 等。这些是**徽标、版本号、键位提示、英文小标签**，属于赛博朋克 HUD 风格的视觉语言，不是需要逐字阅读的正文。字号提升会破坏侧栏纵向高度预算与整体气质。

判定依据：只需「看见」不需「读通」的小字，靠对比度达标即可（已在 P0-2 修到 5.0:1 以上）。

### P2-2 超宽屏阈值 1680 是经验值

不是从无障碍标准推出来的，而是「1920 不触发、2560 收进来」的临界选择。若将来加宽屏专用布局（如双栏并排），这个值要重新定。

## 4. 审查工具自身的两个假阳性（重要）

第一版脚本报出 `scaleBroken=3`（每档缩放都有「元素塌陷」），差点被当成布局 bug 写进报告。逐个打印元素后发现**全是误判**：

| 假阳性 | 真因 | 修正 |
|---|---|---|
| `.storage-head`、`STAGING`、`1.7 GB` 等 `0x0` | `[data-vh-tight] .sidebar-storage { display: none }` 是**有意的让位设计**（窗口矮/缩放大的时候收起 STAGING 信息）。判定只看了元素**自身** display，没看祖先 | 改用 `el.checkVisibility({ checkOpacity: true, checkVisibilityCSS: true })`，能识别「祖先被隐藏」 |
| `<option>` 元素 `0x0` | 原生下拉项本来就不生成布局盒 | 直接排除 `OPTION` 标签 |

修正后 `scaleBroken=0`，说明缩放布局**本来就没坏**。

**这个教训值得记**：审查脚本自己也会说谎。凡是「脚本报出问题」，必须先把问题元素打印出来看清是什么，再决定是修 UI 还是修脚本。否则会照着假阳性去改本来正常的代码。
